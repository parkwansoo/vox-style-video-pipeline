실행 지시서: `docs/작업지시-규칙집행-스크립트화.md` (순서·검증 명령·완료

## 배경과 설계 원칙

이번 편 감사의 결론: **실행 경로에 박힌 검사만 지켜진다.** 독립 도구와
"문서를 읽어라"류 규칙은 전부 실패했다 (mv 규칙 2회 재발, SPEC 6항목
미실행, 입력 모드 사고 30크레딧). 그래서:

1. **검사는 새 진입점이 아니라 이미 필수인 스크립트 안에 심는다.**
   별도 preflight 명령을 만들어도 사람이 잊으면 그만이다 — 잊을 수 없는
   자리(prepare_flow_jobs, assemble)에 넣는다.
2. **예외는 산문이 아니라 기계가 읽는 매니페스트로.** "사유를 남기고
   무시"는 문서 규칙과 같은 약한 강제다.
3. **고정값 대신 실측 계산.** 크롭 기하 고정값은 이미지 세대가 바뀔 때마다
   낡는다 (720:894:0:193 → 720:900:0:190 실측 사례).
4. **통과만 하는 검사는 검사가 아니다.** 각 작업 패키지(WP)는 통과
   케이스와 실패 케이스를 둘 다 실제로 돌려 검증한다.

## WP1 — preflight 매니페스트: 체인 명세와 예외의 기계화 (P0)

**신규 파일** `output/<run>/preflight.json` (편당 1개, 사람이 편집):

```json
{
  "chains": ["5:6", "7:8", "8:9", "10:11", "11:12", "12:13",
             "14:15", "15:16", "17:18"],
  "freshness_exceptions": [
    {"file": "clip1p_end.png",
     "reason": "clip1은 v1 영상 확정 — 재제출 없음", "date": "2026-08-25"}
  ],
  "audio_dup_exceptions": []
}
```

**check_freshness.py 변경**:
- `--run`만 주면 `<run>/preflight.json`에서 chains·예외를 읽는다.
  CLI `--chain`은 덮어쓰기용으로 유지 (기존 호환).
- 예외에 매칭된 낡음은 실패로 세지 않되 **반드시 출력한다**:
  `[예외] clip1p_end.png — clip1은 v1 영상 확정 (2026-08-25)`.
  조용한 통과 금지.
- 예외 항목이 어떤 낡음과도 매칭되지 않으면 `[알림] 낡은 예외 — 정리
  후보`를 출력한다 (실패 아님). 예외가 실제 상황보다 오래 살아남는 것을
  막는 장치다.
- 검사 로직을 `run_freshness(run, chapter, chains, exceptions) -> findings`
  함수로 분리한다 — WP2에서 prepare가 import해 쓴다. CLI·exit 규약(0/2)은
  불변.

**check_audio_dup.py 변경**: 같은 방식의 예외 지원 (현재 필요 0건이지만
구조 대칭). 검사 로직을 `run_audio_dup(manifest, exceptions) -> hits`로
분리 — WP2에서 assemble이 쓴다.

**수용 기준**: ①이번 편에서 위 예외 등록 후 exit 0 ②예외 항목을 지우면
exit 2 재현 ③예외만 있고 낡음이 없는 상태에서 "낡은 예외" 알림 출력.

## WP2 — 검사를 필수 경로에 심기 (P0)

**prepare_flow_jobs.py**: 잡 생성 직후, **이번 run에 포함된 클립에
한정해** 신선도 검사를 자동 실행한다 (import 호출, 서브프로세스 아님).
- 검사 대상: 각 잡의 업로드 이미지(패딩본)가 그 원천(마스터)보다 낡지
  않았는가 + preflight.json chains 중 이번 잡에 해당하는 것.
- 낡음 발견 시 모순 린트와 같은 지위로 **하드 실패** (jobs.json을 쓰지
  않고 종료).
- `--skip-freshness` 탈출구 — 사용 시 `[경고] 신선도 검사 생략`을 출력.

**assemble.py**: 렌더 시작 전에 두 검사를 자동 실행한다.
- **클립 exact-set 검사**: manifest의 모든 클립 파일이 실재하는지 먼저
  확인하고, 하나라도 없으면 **하드 실패** + 빠진 목록 출력. 현재 assemble은
  빠진 클립을 조용히 건너뛴다(부분 합본 실측) — 최종본에서 컷이 사라져도
  신호가 없는 구조다. 부분 합본용 탈출구 `--allow-missing`(빠진 목록을
  경고로 출력하고 진행).
- **오디오 중복 검사**: manifest의 클립별로 나레이션 해당 구간과 파형
  상관, 임계 초과 시 **에러로 중단** + 무음화 명령 안내 (check_audio_dup의
  기존 출력 재사용). `--skip-audio-check` 탈출구 (경고 출력).
  `--timeline-only`일 때는 건너뛴다 (렌더가 없으므로).
- 소요는 19컷 기준 수십 초 — 허용한다.

**SKILL.md**: 6단계(제출 준비)·7단계(조립) 서술에 "자동 검사 포함"을
명시한다. 문서는 안내일 뿐, 강제는 코드에 있다는 원칙 유지.

**수용 기준 (양방향)**:
- 정상: 현재 편 자산으로 prepare·assemble 각각 통과.
- 사고 재현: ①패딩본 mtime을 `touch -t`로 원본보다 9시간 낡게 조작 →
  prepare 차단 ②보존된 사고본(`씬4_몽타주_시안_v1_나레이션중복.mp4`)을
  가리키는 임시 manifest → assemble 차단 (r≈0.999 출력 확인) ③임시
  manifest에서 클립 하나의 파일명을 존재하지 않는 것으로 바꿈 →
  exact-set 검사가 차단, `--allow-missing`이면 경고 후 진행.

## WP3 — Flow 입출력 계약 정합: 패딩본 인지와 크롭 공식 (P0)

**prepare_flow_jobs.py**:
1. docstring 수리 — "항상 1장" 문단을 삭제하고 두 모드(프레임 1장 /
   애셋 2장)와 패딩본 규칙을 서술한다.
2. **패딩본 인지**: chapter_dir에 대응 패딩본(`clipNp.png` /
   `clipNp_first.png` / `clipNp_end.png`)이 있으면 **업로드 대상 =
   패딩본**으로 잡는다. `images[].path`·sha·upload_name은 패딩본 기준,
   원천 마스터 경로는 `images[].master_path`로 함께 기록한다.
   패딩본이 없으면 기존대로 마스터를 쓴다 (패딩 미사용 편 호환).
3. **잡에 `recover_crop` 필드 신설** — 회수 크롭의 정본. 공식:
   - 패딩본 W_p×H_p, 마스터 W_m×H_m. `W_p != W_m`이면 에러 (좌우 패딩은
     이 파이프라인에 없다).
   - 밴드 b = (H_p − H_m) / 2 — 정수가 아니면 에러.
   - Flow 산출 720×1280 기준: `y = round(b × 720 / W_p)`,
     `h = 1280 − 2y` (2y가 짝수이므로 h는 항상 짝수).
   - 기록 형식: `"recover_crop": "crop=720:900:0:190"` + 계산 근거
     (`"pad_geometry": {"padded": [1122,1994], "master": [1122,1402],
     "band": 296}`).
   - 패딩본이 없는 잡은 `recover_crop: null`.
   - 이미지 크기는 PIL로 읽는다 (`.venv`에 있음).
   - **검증 벡터 2개**: 이번 편 1122×1994/1122×1402 → `720:900:0:190`,
     구세대 파일럿(문서 실측: 밴드 498, 콘텐츠 2304) → `720:894:0:193`.
     구세대 실물이 없으면 수치만 단위 테스트로 확인한다.
4. (선택) 패딩본 상단 행이 단색인지 실측해 b와 대조 — 불일치 시 경고만.

**문서 동기화**: SKILL.md 488행 부근의 고정값 서술을 "**jobs.json의
recover_crop이 정본**이며 공식은 위와 같다"로 교체. `flow-browser.md` 등
`894`·`193` 잔재를 grep으로 소탕한다 (과거 기록 인용문은 제외).

**사전 패딩 공용화 (P1 하위 항목)**: 편 전용 `ch1/사전패딩_생성.py`를
`scripts/pad_for_flow.py`로 승격 — 컷별 배경색 실측, **first/end 쌍은 같은
밴드색**(first 실측색을 end에 사용, PROGRESS 08-25 (18) 원칙), 기하 출력.
prepare가 요구하는 파일명 규약(clipNp\*)을 그대로 산출한다.

**수용 기준**: 이번 편 자산으로 prepare 재실행 → jobs.json의 images가
패딩본을 가리키고 recover_crop이 `720:900:0:190`으로 나온다. WP2의
신선도 검사가 "패딩본 vs master_path" 대조로 자연스럽게 이어진다.

## WP4 — 회수 스크립트화: retrieve_flow.py 신설 (P1)

**목적**: 다운로드 이후를 일괄 처리 — 문서를 안 읽어도 스크립트가 올바른
절차를 수행한다. 브라우저 조작(다운로드 버튼까지)은 범위 밖.

**CLI**:
```
retrieve_flow.py --run output/<run> --run-name run-vXX --job ch1-clip8 \
    [--src ~/Downloads/xxx.mp4]
```
- `--src` 생략 시 `~/Downloads`에서 최근 30분 내 mp4를 찾는다. **후보가
  정확히 1개일 때만 진행** — 0개·2개 이상이면 목록을 출력하고 에러
  (자동 추측 금지).

**절차** (각 단계 결과를 출력하고, 실패 시 어느 단계에서 멈췄는지 명시):
1. ffprobe 검증: 720×1280, 길이 = 잡의 `provider_duration_sec` ± 0.1s.
2. **mv**(cp 아님) → `<run>/ch<N>/clip<N>p_raw.mp4`. 같은 이름이 이미
   있으면 기존 파일을 `_vN_사유` 형식으로 먼저 mv 보존 (rm 절대 금지,
   사유는 `--supersede-reason` 인자로 받되 기본 "구버전").
3. jobs.json의 `recover_crop`으로 크롭 → `clip<N>.mp4` (기존 파일 보존
   규칙 동일). `recover_crop`이 null이면 크롭 생략을 명시 출력.
4. `flow_state.py set --stage downloaded --download <경로>` 호출 (기존
   CLI 그대로 — state는 submitted→generating→completed→downloaded 순서
   강제를 이미 한다).
5. `check_clips.py --clips <N>` 실행 — Downloads 잔여 검사 포함이므로
   mv 누락이 구조적으로 잡힌다.
6. 요약 한 줄: 파일·길이·크롭·상태·검사 결과.

**수용 기준**: ①스크래치 폴더에 가짜 720×1280 mp4를 만들어 전 단계
드라이런 통과 ②실패 케이스 3종 — 해상도 틀림 / 길이 틀림 / Downloads에
후보 2개 — 각각 명확한 에러로 중단.

## WP5 — 제품 검증 공용화: check_product.py 신설 (P1)

- `output/20260818-faceoil-3signs/ch1/제품검증.py`를
  `scripts/check_product.py`로 승격. 입력: `--product
  assets/products/<제품>` (SPEC.md + 레퍼런스 이미지), `--image <대상>`.
- **기준값 하드코딩 금지** — 레퍼런스를 대상과 **같은 마스크로 실측**해
  기준으로 삼는다 (08-23 교훈: SPEC의 2.47 하드코딩이 레퍼런스 자신을
  FAIL시켰다). 마스크 파라미터(색 조건)는 제품 폴더의
  `product_check.json`에 두고, 없으면 faceoil 실측값을 초기 템플릿으로
  생성한다.
- 출력: ①수치 판정(실루엣 비율 Δ, 임계는 product_check.json)
  ②레퍼런스-대상 나란히 대조 시트 PNG (라벨 문구처럼 사람이 판정할
  항목용) ③결과 JSON `_검수/제품검증_<이미지명>.json`.
- **강제 지점 (권장안)**: prepare_flow_jobs가 프롬프트에서 `PRODUCT
  LOCK` 블록을 감지하면 해당 클립 이미지의 검증 결과 JSON(PASS)을
  요구한다 — 없으면 하드 실패, `--skip-product-gate` 탈출구(경고 출력).
  이미지 단계에는 필수 공통 스크립트가 없어서, 제출 직전이 마지막으로
  잡을 수 있는 자리다.
- **수용 기준**: 이번 편 확정본 4장(10F·10E·19F·19E) PASS + 반려본
  (`_이전본/` 대형 라벨 gemini본) FAIL 재현.

## 구현 규율 (codex 필수 준수)

- **기존 CLI·exit 규약 불변** — 인자와 동작은 추가만 하고 바꾸지 않는다.
- **에러를 삼키지 않는다** — `2>/dev/null` 금지. 무시한 것은 무엇을
  무시했는지 출력에 남긴다.
- **rm 금지.** 덮어쓰기 전 `_vN_사유` 이름으로 mv 보존.
- 사용자 메시지는 한국어, 코드 주석은 영어 허용 (기존 스타일).
- 의존성 추가 금지 — 표준 라이브러리 + PIL + ffmpeg/ffprobe만.
- `output/`은 git 밖이다 — 커밋은 `scripts/`·`SKILL.md`·`references/`만.
- 셸 검증 시 파이프 뒤 `$?`를 읽지 않는다 (tail의 종료 코드를 읽는 실측
  오판, PROGRESS 08-25 (17)).
- 각 WP 완료 시 위 수용 기준(통과+실패 양방향)을 실제로 돌리고 결과를
  남긴다.

## 구현 순서와 의존

**WP1 → WP3 → WP2 → WP4 → WP5.** WP2는 WP1(예외 매니페스트)과
WP3(패딩본 인지 — prepare의 신선도 검사가 "패딩본 vs 마스터" 대조라서)에
의존한다. WP4는 WP3의 recover_crop을 소비한다. WP5는 독립.

## 범위 밖

- 회고 보고서 원문 수정 6건 — Claude 몫, 사용자 승인 대기 중.
- 비용 대장 4분류(실낭비/정상 재작업/승인 재설계/가정적 방어) — 코드가
  아니라 다음 편 진행상태 문서 양식으로 처리.
- Flow 브라우저 조작 자동화(제출·다운로드 클릭) — 회수 *후처리*만 WP4.
- check_freshness의 MARGIN(30분)·check_audio_dup의 임계(0.5) 조정 —
  실측 근거가 이미 있으므로 건드리지 않는다.
