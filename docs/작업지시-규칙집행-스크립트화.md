## 절대 규칙 (위반 시 작업 중단 사유)

- **실물 자산을 수정하지 않는다.** `output/20260818-faceoil-3signs/`의
  이미지·영상·manifest·jobs는 읽기 전용이다. mtime 조작(touch)도 수정이다.
  사고 재현이 필요하면 **사본 픽스처**(`output/_검증_규칙집행/`)를 만들어
  거기서 한다. 픽스처 정리도 rm 대신 그대로 둔다 (output/은 git 밖).
- **rm 금지.** 덮어쓰기가 필요하면 기존 파일을 `_vN_사유` 이름으로 mv
  보존한다 (retrieve_flow의 보존 로직도 이 규칙의 구현이다).
- **기존 CLI·exit 규약 불변** — 인자·동작은 추가만 한다. 기존 호출
  방식(예: `check_freshness.py --run X --chain A:B`)이 그대로 돌아야 한다.
- **에러를 삼키지 않는다** — `2>/dev/null` 금지. 무시하기로 한 것은
  무엇을 무시했는지 출력에 남긴다.
- **의존성 추가 금지** — 표준 라이브러리 + PIL + ffmpeg/ffprobe만.
  파이썬은 항상 `.venv/bin/python3`.
- 사용자 메시지는 한국어, 코드 주석은 영어 허용 (기존 파일 스타일 유지).
- 셸 검증에서 **파이프 뒤 `$?`를 읽지 않는다** (tail의 종료 코드를 읽는
  실측 오판 사례가 있다). exit 확인은 파이프 없이 한다.
- **설계서와 실물이 어긋나면 임의로 해석하지 말고 중단한다.** 어긋남을
  아래 "발견 기록"에 적고 그 WP를 멈춘 채 다음 독립 WP로 넘어간다.
- 설계 범위 밖 결함을 발견해도 **고치지 않는다** — "발견 기록"에만 적는다.

## 커밋 규칙

- WP 단위로 1커밋. 메시지는 한국어 conventional commit
  (`feat(vox-video): ...` 형식, 본문에 검증 결과 요약 한두 줄).
- 스테이징은 그 WP에서 만진 파일만 명시 경로로. **`output/` 아래는 절대
  스테이징하지 않는다** (gitignore지만 강제 추가 금지).
- push 금지.

      `sheet_only` 3건+`pass` 1건과 현재 이미지 SHA를 확인하고 exit 0.
      `wp5-리포트없음` → JSON 2건 누락으로 exit 1,
      `--skip-product-gate`는 경고 후 exit 0. `wp5-fail`은 검사기
      exit 2 후 prepare가 `status=fail` 2건으로 exit 1.
      `wp5-sha`는 PASS JSON 생성 후 이미지만 교체하자 SHA 불일치로 exit 1.
    - 첫 실행에서 Pillow의 `getdata()` 폐기 예정 경고가 나와
      `load()` 픽셀 순회로 교체했고, 재실행에서 경고가 사라졌다.

## 재개 지시 (2026-08-26, 설계 개정 반영 — Claude)

두 중단 판단 모두 정당했다 — Claude가 재검증으로 확인했고 (PIL 실측·동일

- **WP3**: 폭 동일 하드 조건과 치수 산술을 폐기하고 **비율 기반**으로
  교체 — `master_ratio`(preflight.json 신설 필드)에서 `h = round(720 ×
  H/W)` 짝수화, `y = (1280−h)/2`. 발견 기록의 clip8 반례뿐 아니라
  clip16_end(1124×1399인데 실제 패딩은 720×900 정규 박스)도 치수 산술을
  깨뜨리는 것을 확인했다 — 크롭의 정본은 이미지가 아니라 편의 비율이다.
- **WP5**: aspect 수치축을 **정면·비가림·수직 병 컷 전용**으로 한정
  (`--frontal` 호출자 선언). 10F Δ0.90의 실체는 하이앵글 손 홀드의
  촬영 기하다 — 병 변형이 아니다. 수용 기준은 19E PASS + 반려본 4장
  FAIL + 나머지 3장 sheet_only로 재정의했다. 참고: 10F·19F는 08-23 검증
  통과 후 재생성(하이앵글·클로즈)됐는데 제품검증이 재실행되지 않았다 —
  WP5 게이트가 막으려는 바로 그 구멍이다.

**개정된 설계서·배치 2·배치 5 기준으로 WP3 → WP2 → WP4 → WP5 순서로
재개하라.** WP1 완료분(1718f6f)은 그대로 유효하고, preflight.json의
master_ratio 추가만 WP3에서 소급한다. 완료 기록은 이어서 채운다.
